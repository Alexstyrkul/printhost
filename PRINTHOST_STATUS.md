# PrintHost — текущий статус и незакрытые вопросы

Дата: 2026-09-01. Продолжение `PRINTHOST_PLAN.md` — там исходная задача и архитектура,
здесь — что сделано в ходе реализации и что осталось незакрытым на момент передачи.

Проект: `~/dev/printhost/`. Сборка: `./build.sh` (см. тот файл, пайплайн проверен,
работает). Установка: `adb install -r out/signed.apk`, дальше `adb forward tcp:8899 tcp:8899`
и дашборд на `http://<IP телефона>:8899/`.

## Железо и прошивка (важные факты, добытые вживую)

- Принтер: Ender-3 V3 SE, Marlin V1.0.6 (Sep 19 2023), CH340 serial.
- Baud rate 115200 подтверждён рабочим.
- **M28 (запись на SD) требует классическое имя 8.3** (max 8 симв. + точка + 3 симв.
  расширения), несмотря на заявленную поддержку `Cap:LONG_FILENAME:1` (та работает только
  для чтения/просмотра, не для записи по serial). Длинные имена от слайсера получают
  `open failed`. Решение уже есть: `PrinterService.toSafeSdFilename()` — автоматическое
  сокращение с сохранением детерминированности (одно и то же исходное имя → одно и то же
  короткое, чтобы повторная загрузка перезаписывала, а не плодила алиасы).
- **Во время записи (`M28`) прошивка требует протокол line-number + checksum**
  (`N<n> ...*<checksum>`) для любого не-`M29` содержимого — без этого команда отклоняется
  с `Error:No Checksum with line number` + `Resend:`. Реализовано в
  `PrinterConnection.sendNumberedLineWithResend()` + `marlinChecksum()`.
- Прошивка **посимвольно обрезает всё после `;`** уже на приёме строки — то есть комментарии
  (и любой checksum, случайно оказавшийся после `;`) физически не долетают до неё. Поэтому
  комментарии стрипаются на нашей стороне перед отправкой (`stripComment()`) — это не потеря
  данных, а то же самое, что сделала бы сама прошивка.
- **`M110 N0`** (сброс счётчика номеров строк) обязателен перед каждым `M28`, потому что
  счётчик персистентен между подключениями и предыдущие неудачные попытки могли увести его
  вперёд. `M110` сам должен идти через N/checksum-обёртку (содержит букву N) и обязательно
  **до** `M28`, иначе он попадёт в сам файл как лишняя строка (прошивка во время записи пишет
  в файл вообще всё, что получает, кроме `M29`).
- Прошивка нормализует концы строк в `\r\n` при записи → реальный размер файла на карте
  = сумма (длина_строки_без_комментария + 2) по всем непустым строкам. Именно так считается
  `expectedBytes` для проверки.
- **`M20` (список файлов) не обновляет размер для только что записанных файлов** — всегда
  показывает 0 для файлов, созданных через `M28`. Поэтому проверка целостности сделана через
  **`M23` (выбор файла)** — он честно возвращает реальный размер в ответе
  (`File opened: X Size: N`). `M23` не запускает печать (это делает только `M24`), так что
  использовать его для верификации безопасно. Тот же приём (`PrinterConnection.selectFile()`)
  теперь переиспользуется и для выбора файла на печать без повторной загрузки (см. ниже).
- **`M20 L` (запрос длинных имён) на этой прошивке ничего не даёт для наших же файлов** —
  подтверждено вживую: байт-в-байт совпадает с обычным `M20`. Причина не в прошивке, а в
  нас самих: `M28` пишет файл только под коротким 8.3-именем, поэтому в FAT32-записи
  физически нет LFN-компонента, который `M20 L` мог бы показать. При этом для файлов,
  скопированных на карту напрямую с компьютера (кард-ридер), LFN в файловой системе
  действительно есть, и `M20 L` его показывает как есть. Решение — гибридное, см. "SD file
  browser" ниже.
- **`M105` при бланкирующей команде из файла (`M109`/`M190` — нагрев-и-ждать) не отвечает
  сразу** — Marlin обрабатывает одну очередь команд, и наш `M105`, посланный поверх serial,
  встаёт в очередь ЗА уже выполняющимся блокирующим `M109`/`M190` из самого print-файла.
  Пока идёт нагрев, прошивка шлёт `echo:busy: processing` keepalive-сообщения и спонтанные
  температурные авто-репорты, но БЕЗ `ok` — это нормальное поведение Marlin
  (busy-keepalive-протокол), не сбой. **См. открытую проблему #1 ниже — всё ещё не
  почищено.**
- Ответ на `M105` иногда приходит **в той же строке, что и `ok`**
  (`ok T:26.14 /0.00 B:26.00 /0.00 ...`), а не отдельной строкой перед `ok` — уже
  обработано в `PrinterConnection.waitForOk()`.
- USB-permission диалог у принтера **не имеет чекбокса "запомнить"** — но реально permission
  переживает перезапуск приложения, пока устройство физически не отключено от порта.
  Диалог требует **включённого экрана** телефона, чтобы `dev.oleksandr.usbtap`
  (accessibility-сервис на этом же телефоне) успел его подтапнуть — при выключенном экране
  диалог всплывает, но не тапается.
- Камера: захват 640x480 (landscape), после поворота под портретный сенсор — 3:4. Сверено
  вживую сырой MJPEG-поток (`/camera/stream` напрямую, без рамки дашборда) с тем, что видно
  в уменьшенной рамке (`max-width:240px`) — картинка идентична, поле зрения не обрезается,
  просто отображается мельче. Ложное ощущение "обрезки" было из-за уменьшенного размера
  рамки, не из-за реальной обрезки кадра.
- На карте обнаружен `CLIP.GCO` — 0 байт даже по честному `M23`-стату, не только по глючному
  `M20`. Судя по всему, огрызок с более ранних тестов протокола `M28` (прерванная/тестовая
  запись), не настоящий gcode. Печатать нечем, но и удалить нечем — см. проблему #4 ниже.

## Whitelist — работает как задумано

Все команды из исходного плана реализованы и вживую протестированы (кроме реального полного
прогона печати до конца — см. ниже): `M115`, `M851`, `M28`+контент+`M29`, `M20`/`M20 L`,
`M23`+`M24` (start), `M25` (pause), `M25`+`M524` (stop), `M24` (resume), `M105`/`M27`/`M31`
(poll). `M112` и вся ветка Emergency Stop **удалены по явному запросу пользователя** — вместо
этого Pause/Resume с подтверждающими диалогами в UI на Pause и Stop. `M30` (удаление файла)
реализован (`DELETE`-кнопка в блоке "On SD Card"), но **точная формулировка ответа прошивки
на ошибку не подтверждена вживую** — на момент реализации карта оказалась пустой (см. ниже),
проверить не на чем. `PrinterConnection.deleteFile()` пока не парсит ответ на предмет ошибки,
просто возвращает его как есть — при первом реальном использовании нужно свериться и, если
нужно, добавить обработку по образцу `selectFile()`'s "open failed".

## ⚠️ Незакрытые проблемы (по приоритету)

### 1. Опрос статуса падает по таймауту во время нагрева (M109/M190) — ИСПРАВЛЕНО, ПОДТВЕРЖДЕНО ЖИВЬЁМ
`PrinterConnection.waitForOk()` переделан на скользящий таймаут: дедлайн сбрасывается при
получении ЛЮБОЙ строки (не только `ok`), с жёстким потолком `HARD_TIMEOUT_MS = 180_000`
(3 минуты) на случай реально мёртвого соединения. Добавлен `LineListener` — `pollTemperatures()`
теперь принимает колбэк на каждую промежуточную строку; `PollerThread.pollOnce()` в
`PrinterService` его использует, чтобы `T:`/`B:` из спонтанных авто-репортов сразу попадали в
`state`, не дожидаясь формального `ok`. **Подтверждено на реальном прогоне** (2026-09-01):
хотэнд грелся 71°→220° под активным опросом статуса — раньше это гарантированно валило
приложение в `ERROR` за 5 секунд, сейчас ни разу не сорвалось за всё время нагрева.

**Важный смежный факт, обнаруженный в этой же сессии**: пока идёт блокирующая `M109`/`M190`,
прошивка выполняет её как ОДНУ команду и не переходит к следующей из очереди (`M25`, `M524`
и т.п.), пока не достигнет целевой температуры — это не баг нашего кода, а архитектура Marlin
(gcode-очередь строго последовательна; `M105` получает ответ во время нагрева благодаря
специальной обработке ВНУТРИ самого busy-wait цикла M109, а `M25`/`M524` такой обработки не
имеют). Экранные кнопки принтера (DWIN) реагируют мгновенно даже во время нагрева, потому что
опрашиваются через `idle()`, который Marlin вызывает даже находясь внутри блокирующего
ожидания — у serial-команд такого пути нет. Практическое следствие: `Pause`/`Stop`,
отправленные во время начального разогрева, физически не могут сработать раньше, чем нагрев
дойдёт до цели — это подтверждено пользователем вживую несколько раз подряд (пришлось
останавливать печать вручную на экране принтера, пока шёл нагрев). Не баг, но важное UX-
ограничение, см. #6 ниже — оно же помешало довести до конца живую проверку нового `stopPrint()`.

### 2. `PrinterConnection.isOpen()` даёт ложное "подключено" — ИСПРАВЛЕНО, ЖДЁТ ПРОВЕРКИ ЖИВЬЁМ
Оба конкретных места починены:
- `writeRawBytes()`/`readLine()` в `PrinterConnection` теперь ловят `IOException` от реального
  I/O (`port.write`/`port.read`), сами вызывают `disconnect()` (обнуляют `port`) и
  прокидывают исключение дальше — `isOpen()` сразу отражает реальность после первой же
  неудачной операции, а не врёт бесконечно.
- `connectPrinter()` в `PrinterService` больше не делает ранний `return true` по `isOpen()` —
  явный клик Connect всегда идёт на чистый `disconnect()`+`connect()`. Дёшево в здоровом
  случае: кнопка Connect в дашборде и так скрыта, пока принтер реально подключён, так что этот
  путь срабатывает только когда пользователь реально пытается восстановиться из
  DISCONNECTED/ERROR.

**Частично подтверждено косвенно**: в ходе сессии один раз своими глазами видел, как
приложение само перешло из `ERROR` ("No supported USB-serial device attached") обратно в
`Uploading...`/рабочее состояние без ручного рестарта сервиса — это ровно тот сценарий, который
раньше был сломан. Но это было замечено постфактум, не как контролируемый тест с чистыми
логами до/после — честной целенаправленной проверки (спровоцировать обрыв → нажать Connect →
убедиться) не делали.

### 3. USB-устройство переподключается само по себе — ПРИЧИНА ВСЁ ЕЩЁ НЕ УСТАНОВЛЕНА
Корень проблемы не искали в этой сессии (нужна живая диагностика с чистыми логами — см. ниже),
но **фикс #2 напрямую смягчает симптом**: раньше самопроизвольный обрыв USB навсегда ломал
`isOpen()` в состояние "подключено", и кнопка Connect молча ничего не делала — восстановиться
можно было только полным рестартом сервиса. Теперь после обрыва `port` обнуляется сам, и
Connect должен честно переподключаться. Это не решает, ПОЧЕМУ устройство мигает на шине —
только даёт приложению шанс пережить это без ручного рестарта.

В `dumpsys usb`/logcat видно постоянную смену `device_address`
(/001/003 → 004 → 007 → 008 → 002...) и `ENOENT` при попытке открыть — устройство реально
дёргается на шине. **Пользователь считает маловероятной версию про кабель**, поскольку до
этого (загрузка ~1.17 МБ на SD) всё было стабильно на том же физическом соединении. Открытые
гипотезы для проверки:
- корреляция с нагревом/просадкой питания на плате принтера (не на USB-кабеле) во время
  сильного нагрева хотэнда+стола одновременно;
- что-то в самой команде `M524`(abort) вызывающее сброс платы/watchdog;
- поведение `drainBootNoise()`/DTR при каких-то условиях реконнекта.

Нужно воспроизвести с чистыми логами (снять `dumpsys usb` и logcat подряд, без собственных
вмешательств между) и смотреть, что именно предшествует первому "миганию".

### 4. `M30` (удаление файла) — РЕАЛИЗОВАНО, ПОДТВЕРЖДЕНО РАБОЧИМ
`PrinterConnection.deleteFile()`, `POST /delete`, кнопка-корзина в UI — пользователь подтвердил
вживую, что удаление работает. Формат ответа прошивки на ОШИБКУ удаления (несуществующий файл)
всё ещё не проверен (`deleteFile()` не парсит ответ на предмет ошибки) — не критично, можно
свериться при первом реальном столкновении.

### 6. Stop (`M25`+`M524`) не совпадает с физической кнопкой Stop — НАЙДЕНА ПРИЧИНА, ИСПРАВЛЕНО, ЖДЁТ ПОВТОРНОЙ ПРОВЕРКИ
Обнаружено на реальном прогоне (2026-09-01, живая печать `Desk_Cable_Management...`): после
`/stop` из дашборда экран принтера (DWIN) продолжал показывать "Пауза", финишная презентация
модели не происходила, пользователю пришлось нажимать Stop вручную прямо на экране.

**Причина найдена в исходниках прошивки** (репозиторий `CrealityOfficial/Ender-3V3-SE` на
GitHub, публичный, GPL) — конкретно:
- `Marlin/src/gcode/sd/M524.cpp`: `M524` вызывает настоящий abort (`card.abortFilePrintSoon()`)
  **только если `IS_SD_PRINTING()` истинно**; иначе просто `card.closefile()` — тихо ничего не
  делает по сути. Старый код нашего `stopPrint()` слал `M25` (пауза) **перед** `M524` — а `M25`
  на этой прошивке идёт через `M125` (park-on-pause), что сбрасывает `IS_SD_PRINTING()` в false.
  То есть мы сами гарантированно попадали в "тихий" fallback-путь `M524`.
- `Marlin/src/lcd/dwin/e3v2/dwin.cpp` (обработчик физической кнопки Stop на тачскрине)
  вызывает `card.abortFilePrintSoon()` **напрямую**, в обход `M524`-обёртки и её проверки — и
  ДО этого синхронно гасит нагрев (`thermalManager.disable_all_heaters()` +
  `setTargetHotend(0,0)`/`setTargetBed(0)`), тогда как голый `M524` только выставляет флаг,
  который асинхронно подхватывает главный цикл прошивки — отсюда и ~35 сек задержки, которые
  видели в логах раньше.

**Фикс**: `PrinterConnection.stopPrint()` больше не шлёт `M25` — теперь `M104 S0` + `M140 S0`
(мгновенный сброс таргетов, как делает сам экран) и сразу `M524`, пока `IS_SD_PRINTING()` ещё
истинно. Для случая "Stop нажат из состояния PAUSED" (где `IS_SD_PRINTING()` и так уже false)
добавлен отдельный `PrinterConnection.stopPausedPrint()`: те же `M104 S0`/`M140 S0`, затем
кратковременный `M24` (резюме) чтобы снова сделать `IS_SD_PRINTING()` истинным, и сразу `M524`.
`PrinterService.stopPrint()` теперь выбирает нужный вариант по `state.phase`.

**Собрано и установлено, но НЕ ПРОВЕРЕНО живьём end-to-end с новым кодом.** Каждая попытка
проверить в этой сессии натыкалась на #1's смежный факт: Pause/Stop, отправленные во время
начального разогрева файла (блокирующий `M109`/`M190`), физически не могли дойти до прошивки,
пока не закончится нагрев — пользователю приходилось останавливать печать вручную на экране
принтера, не дожидаясь ответа от приложения. Ни разу не дошли до того, чтобы нажать
Stop/Pause уже ПОСЛЕ разогрева, когда идёт реальное движение — то есть новый `stopPrint()`
(`M104 S0`+`M140 S0`+`M524`, без `M25`) и `stopPausedPrint()` (то же + краткий `M24` перед
`M524`) технически ни разу не выполнились на реальном железе в этой сессии. Обоснование фикса
железное (взято из исходников самой прошивки, не догадка), но **живого подтверждения "экран
показал завершение, а не паузу" пока нет** — это первое, что нужно перепроверить на следующем
прогоне, дождавшись окончания разогрева перед тем как жать Stop.

Полностью экран (DWIN UI state / `checkkey`/`Popup_Window_Home`) всё равно программно
недостижим — туда нет пути через serial gcode вообще, это внутреннее состояние touch-экрана.
Но нагрев и job теперь должны гарантированно и быстро останавливаться, максимально близко
повторяя то, что делает сама кнопка на экране — как только реально проверим на практике.

### 5. Обдув (fan speed) — ОТКЛОНЕНО ПОЛЬЗОВАТЕЛЕМ, не делать
Backend-парсинг из gcode (`GcodeFanParser`) уже есть и не используется в UI. Пользователь
явно подтвердил в этой сессии, что фича не нужна — не возвращать в UI без отдельного запроса.

## Формат ответа принтера — на будущее, если снова придётся разбирать протокол

Пример реального `M105`-ответа этой прошивки:
```
ok T:150.20 /0.ok T:146.75 /0.00 B:44.64 /0.00 @:0 B@:0 FAN0@:0
```
Обратите внимание — тут даже видна склейка двух ответов в один (баг/особенность буферизации
на стороне прошивки при частых запросах), это тоже стоит учитывать при доработке парсера
temperature-ответов.

Пример реального `M20`-ответа (короткие имена, размер, и посторонняя Spotlight-запись —
`/sdfiles` фильтрует и то, и другое где нужно):
```
Begin file list
CLIP.GCO 0
/SPOTLI~1/STORE-V2/02B45F~2/TM~5.GLO 0
DESK_~EC.GCO 1173106
End file list
```

## Мелкие детали реализации, чтобы не тратить время на повторное открытие

- Порт HTTP-сервера: 8899 (сознательно не 2525, чтобы не путать с 3D Fox).
- `commandLock` (не `synchronized(this)`) — отдельный объект-мьютекс в `PrinterService`,
  чтобы долгая загрузка не блокировала `/status`-поллинг дашборда. Это уже пофикшено и
  протестировано (статус живо обновляется во время многоминутной загрузки).
- Camera2: `JPEG_ORIENTATION` выставляется по `SENSOR_ORIENTATION` камеры — фикс поворота
  видео сделан, визуально сверен в этой сессии (сырой поток совпадает с рамкой дашборда,
  без обрезки).
- Дизайн собирался и итерировался через Claude Design canvas-скилл (`~/dev/printhost/design/`,
  артефакт `https://claude.ai/code/artifact/37ff4b40-089d-4fa7-94bd-daedd6280d2a`) — там
  финальная одобренная версия макета, если нужно свериться визуально. Из неё в реальный
  `assets/dashboard.html` в этой сессии перенесены все три пункта дизайна (см. выше).
- Новый класс `SdFilenameMap.java` — единственная ответственность: короткое 8.3-имя →
  читаемое имя, персистентно в `getFilesDir()/sd_filename_map.json`, best-effort (порча
  файла не валит приложение, просто теряется часть читаемых имён).
- `adb forward tcp:8899 tcp:8899` временами роняет отдельные запросы
  (`net::ERR_EMPTY_RESPONSE` на `/status` в консоли браузера) — известная нестабильность
  самого туннеля, не связана с кодом приложения; `refreshStatus()` уже глотает такие ошибки
  молча, ничего чинить не нужно.
- **Java-лямбды не собираются этим тулчейном** — `javac` падает с
  `cannot find symbol: method metafactory` (bootclasspath для компиляции не тянет
  `java.lang.invoke.LambdaMetafactory`, хотя `-source/-target 8` формально его допускают).
  Подтверждено на реальной попытке в этой сессии. Везде, где нужен колбэк/интерфейс
  (`PrinterConnection.LineListener` и т.п.) — использовать анонимные классы
  (`new Foo() { ... }`), как и весь остальной код в проекте, а не лямбда-синтаксис.
- Правило для себя (не для кода): не писать/загружать собственный gcode для тестов поведения
  принтера — только реальные файлы от слайсера, которые уже есть в проекте, или то, что
  загружает сам пользователь.
